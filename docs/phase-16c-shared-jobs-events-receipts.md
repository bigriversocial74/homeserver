## Initial gaps

HomeServer already had supervised local agents, Microgifter jobs, POD voice jobs, provider queues, approvals and receipts, but they were separate contracts. The missing shared layer included:

1. A wrapper-neutral job envelope.
2. Exact wrapper, connection, grant and authority-revision binding.
3. Shared idempotency, correlation and causation identifiers.
4. Worker identity and bounded leases.
5. Revocation-aware cancellation of queued and leased work.
6. Private-input and private-result separation.
7. HomeServer-controlled safe-result projection.
8. Safe provenance summaries without source identifiers or source content.
9. Append-only job events and immutable execution receipts.
10. Offline delivery, replay and acknowledgement.

## Authority model

- A wrapper may submit a job only through a Phase 16B authorization decision.
- Job submission captures the wrapper ID, connection ID, grant ID, grant revision, connection authority revision and authorization decision ID.
- Workers cannot alter any authority field.
- Agent workers do not gain independent authority from receiving a job.
- A changed connection authority revision, inactive grant, expired grant, revoked wrapper or denied authorization receipt cancels executable work.
- `action.propose` produces proposals only. It cannot execute an external action.

## Private-data boundary

- Full job inputs are stored only in `wrapper_job_inputs` with classification `private`.
- Full execution results and provenance are stored only in `wrapper_job_private_results`.
- Wrapper snapshots never read either private table.
- Wrapper-visible results are generated by HomeServer according to the captured result policy and explicit field allowlist.
- Credential-like content, private source fields, prompts, memory, local paths, raw documents and full conversation content are rejected from safe projections.
- Wrapper-facing provenance includes counts, source types and evidence hashes only.

## Job state model

`queued → leased → running → completed`

Additional transitions:

- `queued|leased|running|waiting → cancelled` when authority changes or a user cancels.
- `queued|leased|running|waiting → expired` when the job lifetime ends.
- `leased|running → queued` after a retryable failure or recoverable expired lease.
- `leased|running → failed` after a non-retryable failure.
- `leased|running → dead_letter` after retries are exhausted.

Every terminal state requires an immutable execution receipt and an offline delivery record.

## Idempotency and replay

- Idempotency is scoped to one wrapper connection.
- Reusing an idempotency key with the identical request hash returns the existing job.
- Reusing it with a changed request or payload hash fails closed.
- Delivery polling may replay an unacknowledged receipt.
- Acknowledgement requires the exact receipt hash.

## Worker and lease model

- Workers have a stable local ID, kind, declared job types, concurrency limit, revision and revocation state.
- Claiming returns a one-time raw lease token; SQLite stores only its SHA-256 hash.
- Leases are bound to the exact job and worker.
- Start, heartbeat, completion and failure require the active lease token.
- Leases cannot outlive job expiration.
- Expired leases are retried only when attempts, expiration and current authority allow it.

## Safe result policies

- `receipt_only`: no result body.
- `metadata_only`: fixed metadata fields only.
- `aggregate_only`: numeric, Boolean, null and bounded aggregate structures only.
- `proposal_only`: bounded proposal fields; proposed actions remain explicitly approval-gated.
- `safe_result`: exact top-level field allowlist from the Phase 16B scope.

All policies enforce bounded depth, collection size, string length, result bytes and forbidden private/credential fields.

## Events and receipts

Job events are append-only and include sequence number, state transition, outcome, actor, visibility, detail code, metadata and event hash.

Execution receipts are immutable and bind:

- job, wrapper and connection IDs
- grant and connection authority revisions
- authorization decision
- capability and operation
- idempotency, request and payload hashes
- approval and plan hashes
- correlation and causation IDs
- outcome and result code
- safe-result and provenance hashes
- worker identity and attempt count
- start/completion timestamps
- receipt hash

## Offline behavior

Jobs may continue locally while a wrapper connection is in `offline` or `grace` state if its authority remains valid. Terminal receipts remain in a pending delivery queue. Reconnection polling returns safe job data and receipts only. Delivery is complete only after receipt-hash acknowledgement.

## Explicit exclusions

Phase 16C does not replace provider-specific workers. It supplies the shared authority, queue, evidence and delivery contract around them. Provider adapters will migrate incrementally.

Phase 16C does not execute arbitrary external actions. Sensitive execution remains separately approval-gated and will use the shared job contract in later integration phases.

## 10/10 certification gates

1. Pairing without a grant cannot submit a job.
2. Wrapper A cannot list, claim, cancel, deliver or acknowledge Wrapper B work.
3. Changed grant or connection authority cancels queued and leased jobs.
4. Idempotent replay returns one job; changed payload replay fails.
5. Raw lease tokens never enter SQLite.
6. Private inputs and full results never appear in wrapper snapshots or receipts.
7. Safe result policies and byte limits are enforced.
8. Every terminal job has one immutable receipt and one delivery record.
9. Offline replay and hash-bound acknowledgement pass.
10. Formatting, native tests, strict lint, retained phases, installer, LocalSystem, signed-update and rollback certification pass on the exact final head.
